# Task: write one new held-out eval case (h5)

You'll write one synthetic dataset with known answers. We use it to check whether a recent fix to our data-analysis agent works on data nobody has seen. It takes about half a day. You need Python, pandas and some statistics; you don't need to know the agent's code.

## Background

**The project.** An LLM agent that takes a CSV and writes an analysis report. A "lead" agent plans tasks, specialist agents write and run Python for each task, and the lead writes the report from what the code recorded. Every number in the report must match a value the code recorded.

**How we measure it.** An eval case is a dataset with planted answers:

- things the report must find;
- one or two tempting wrong conclusions it must not claim;
- caveats it should mention.

The agent runs on each case 3 times. An LLM judge reads each report and marks every expected finding yes / partly / no, and every forbidden claim as made or not.

- **Dev cases** (`evals/cases/`, 12 of them) are the ones we develop against.
- **Held-out cases** are written by someone other than the developer and kept out of sight until they run once. Results on them show whether a change generalises or only fits the dev cases. The first four (h1–h4) are in `evals/heldout/`.

**What happened.** The Phase 3 agent passed three of the four held-out cases. It failed **h3**, which you can read in full:

- `evals/heldout/cases/h3.yaml` and `ho_shipments` in `evals/heldout/generators.py`: the case;
- `check_h3` in `evals/heldout/test_cases.py`: its checks;
- [phase3.md](phase3.md), "By case" and "After the run": what the agent did.

In h3, 150 of 1,000 parcels have weight `0.0`. Real weights start at 0.2 kg, so these are missing values stored as zeros. Pandas doesn't count them as missing, and those parcels are slow. Across all rows, heavier parcels therefore *look* faster. The agent reported "heavier parcels are delivered faster" in 2 of 3 runs. The dev suite has the same trap in `diabetes` (the well-known Pima dataset, with zeros in its medical measurements). The agent passed that every time, most likely because it knows Pima from training.

**The fix.** Before any task runs, the agent computes a profile of the dataset and gives it to the lead. The profile used to say "Missing values: none", counting empty cells only. It now says "Empty cells". It also lists, for every numeric column (and a numeric target), its min, 1st percentile, median and max. It adds the most common value **only when that value covers at least 1% of rows**. The profile only states these values; it doesn't call any of them suspicious. For h3 it reads:

```
- Empty cells: none
- Numeric columns:
  - parcel_weight_kg: min 0, 1st pct 0, median 3.735, max 35.12; most common 0 (150 of 1,000)
  - distance_km: min 5.6, 1st pct 9.585, median 152.1, max 300
  - items: min 1, 1st pct 1, median 6, max 10; most common 1 (106 of 1,000)
  - delivery_hours: min 15.7, 1st pct 19.49, median 36.65, max 90.6; most common 37.6 (11 of 1,000)
```

The code is `profile_summary` in `agent/profiling.py`. With the fix, h3 went from 2.5 false claims in 3 runs to none. But the fix was built while looking at h3, so h3 no longer proves anything. That's why we need your case.

## Your task

Write **one case, `h5`**, that answers this question: *does the agent catch a value that stands in for "missing" when it is not a zero in a weight column, and does it avoid the conclusion that value distorts?*

### Must-haves

1. **The placeholder fills the cell.** `df.isna().sum().sum() == 0`. That's the whole trap.
2. **There's a tempting wrong conclusion, and a naive analysis really reaches it.** Examples: a reversed sign, an effect that isn't there, or a real effect hidden. The case can only fail on a false claim if there is one to make. Put it in `must_not_claim`.
3. **Different from h3 and Pima** in all three of these: the placeholder value, the kind of column, and the domain.
4. **A fair dataset:**
   - generated by your code, not a known dataset;
   - 60–2,000 rows, 4–10 columns, one target;
   - planted effects strong enough to recover with a plain test at your seed.
5. **Neutral names.** The agent sees the CSV name and the column names (`pure_noise.csv` once gave an answer away).
   - Don't use words like `missing`, `unknown`, `code` or `flag` in them.
   - **Don't reuse any CSV name** from `evals/cases/` or `evals/heldout/cases/`. The harness reuses an existing file of the same name in `evals/data/`, so a clash silently runs the wrong data.

### Your choices

Vary these from h3:

- **The value:** for example −1, 99, 999 or 9999, or a date like 1900-01-01.
- **Where it sits:** in a feature or in the target. The target can be numeric, binary or a string label.
- **How many rows it covers,** and whether those rows differ in the target (as in h3) or are random.
- **How the distortion shows.**

One decision to make deliberately:

- **A value the profile shows**, at an extreme or as the most common value with at least 1% of rows, tests whether **the fix generalises**. That's the question we need answered now.
- **A value it doesn't show**, such as an in-range value or one covering under 1% of rows, tests the agent's own care beyond the fix. That's fair but harder. Say which kind you chose in the case's `description`.

### Out of scope

- Changing the agent, the profile, the judge, or h1–h4.
- Running the agent on your case, even once. It costs API money, and choosing a case by how the agent does on it biases the test.

## Files

Put everything in **`evals/heldout2/`**. It's gitignored, so nothing you write shows up in `git status` or a diff. Use h3's files as templates.

```
evals/heldout2/
  generators.py        # GENERATORS = {"<name>": function(seed) -> DataFrame}
  cases/h5.yaml
  test_h5.py
```

**`generators.py`**
- Use a seeded `np.random.default_rng(seed)` and return a DataFrame with values rounded to a few decimals.
- Give the generator a name that clashes with nothing in `evals/generators.py` or `evals/heldout/generators.py`. A prefix such as `h5_` works.
- You may import helpers: `from evals.generators import _logistic`.

**`cases/h5.yaml`**

| Field | What it holds | Read by |
|---|---|---|
| `description` | The trap and the answers, in plain words | people only |
| `file` | Neutral CSV name | the agent |
| `target` | Target column | the agent |
| `data` | `{generator: <name>, seed: <int>}` | the harness |
| `facts` | `{name, value, near: [keywords]}`: an exact value the report should state, such as the placeholder's count | a script: the value must appear on a line with one of the keywords |
| `must_find` | 3–5 sentences, one claim each, with direction and rough size | the judge |
| `must_not_claim` | 1–2 tempting wrong conclusions, worded as a report would put them | the judge |
| `caveats` | `{name: [keywords]}`: limitations the report should mention | the judge |

**`test_h5.py`** must check that:
- the case loads (`load_case("h5")`) and `all_cases("heldout2")` lists it;
- the generator gives the same data for the same seed;
- there are no empty cells;
- every `facts` value equals what you compute from the data;
- every `must_find` effect is recoverable once the placeholder is handled, with the right direction and p well below 0.05;
- the trap is real: the naive analysis, with the placeholder left in, gives the `must_not_claim` conclusion.

`check_h3` shows the pattern. Load the generator from `evals/heldout2/generators.py` the way h3's test loads its own.

Run the tests with `uv run pytest evals/heldout2 -q`. They should pass.

## Done when

1. `uv run pytest evals/heldout2 -q` passes.
2. You've recorded the hash, which covers every file without revealing any of them:
   ```bash
   tar --sort=name --mtime=@0 --owner=0 --group=0 --numeric-owner \
       --exclude=__pycache__ -cf - -C evals heldout2 | sha256sum | tee evals/heldout2.sha256
   ```
3. You've told the owner it's in, and named the kind of value you chose (shown by the profile or not). Say nothing else about the case.

After the hash is committed, don't change the files. If you find a bug before the run, fix it, record a new hash, and say why in the commit message.

## What happens next

The owner checks the hash. Then h5 runs 3 times with the fixed agent (`v0.3.1`) and 3 times with the old baseline agent. h1, h2 and h4 also run 3 times with the fixed agent, to check the fix didn't break them. The results are reported apart from the Phase 3 numbers.

The goal is met only if every run of the fixed agent is free of false claims, and the agent finds more than the baseline.
